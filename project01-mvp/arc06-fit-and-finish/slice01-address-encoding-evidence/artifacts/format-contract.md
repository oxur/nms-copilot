## Contract readback before investigation

The current core `GalacticAddress` is an intentional 48-bit portal-frame value. Its field order is `P-SSS-YY-ZZZ-XXX`; the galaxy/reality index is a separate `u8`. `from_packed` masks to 48 bits, so it cannot be changed globally to decode a different save representation without breaking its current public contract (`crates/nms-core/src/address.rs:34-117`). `PortalAddress` is exactly 12 nibbles and converts to/from that core value (`address.rs:352-544`).

The save model nevertheless uses one `PackedGalacticAddress(u64)` for both `DiscoveryData.DD.UA` and persistent base `GalacticAddress`, while the expanded player `UniverseAddress` has distinct integer coordinate fields plus `RealityIndex` (`crates/nms-save/src/model.rs:80-165,197-239,279-322`). The current conversions route discovery and base values through the truncating core constructor and force galaxy zero; expanded player values use their explicit reality index (`crates/nms-save/src/convert.rs:35-108`). This establishes a suspect shared boundary, not proof that the two packed save fields share a layout.

The closeout packet requires the independently supplied Chili portal witness and a portal-shaped control to stay distinct. It also keeps zero, negative, width, missing-field, and galaxy behavior open until observations support a decision. The future repair can introduce save-specific types/functions at the save boundary; it must preserve the core portal contract, propagate representation identity through graph, watch, query, and cache, and must not turn absent/malformed values into successful zero addresses (API-37 SHOULD; AP-33 AVOID).

## Downstream identity and cache/query effects

`extract_systems` decodes both system and planet DD.UA values using `from_packed(..., 0)`, builds `SystemId` from each address, takes the planet index from the decoded low-48 address, and groups planets by the resulting system ID (`crates/nms-graph/src/extract.rs:104-177`). `SaveSnapshot::from_save` uses that result and indexes planets by `(SystemId, planet_index)`; it separately uses expanded player conversion and base conversion (`crates/nms-watch/src/snapshot.rs:13-61`). A different decode changes graph keys, watch deltas, query associations, route indexes, and cache contents.

`execute_find` formats `portal_hex` from `system.address.packed()` while retaining the selected `planet` in `FindResult`; a result's portal glyph planet nibble may therefore need to incorporate `result.planet.index` even when the system address contains another planet component (`crates/nms-query/src/find.rs:138-160`). Its biome-only unconstrained branch joins planets to the first system with the same planet index across the entire model, which already causes wrong associations for repeated indices (`find.rs:92-116`, corroborated by closeout F03). Keep that association defect separate from the packed-address repair while planning affected oracles.

The rkyv `CacheData` serializes decoded `GalacticAddress` values and carries `save_version`/`cached_at`, but no decoder/schema version (`crates/nms-cache/src/data.rs:9-46`). Cache freshness uses only cache-vs-save mtimes (`freshness.rs:15-29`) and a fresh cache is rebuilt directly without reparsing the save (`freshness.rs:46-64`). A later decode change must invalidate/re-key derived cache data or otherwise ensure old decoded identities are not reused. `SystemId`/graph indices derive from packed address identity; inspect the `SystemId` implementation during repair (`crates/nms-core/src/system.rs:13-25`).

## Bounded next repair recommendation

1. **Do not edit `nms-core::GalacticAddress::from_packed` or the portal parser to solve save decoding.** Add a distinct save-domain newtype/function only after the packed layout is independently specified; separate discovery DD.UA and persistent-base address types unless a decoder/reference proves they share format. Keep expanded `UniverseAddress` conversion on its existing structured-field route.
2. **For discovery repair,** cover `nms-save/src/model.rs` field types and serde behavior; `nms-save/src/convert.rs::RawDiscoveryRecord::to_core_record`; `nms-graph/src/extract.rs::extract_systems`; then verify `GalaxyModel` identity/index construction, `nms-watch::SaveSnapshot`, `nms-query::execute_find` glyph generation, CLI/REPL/MCP renderers, and cache invalidation (`nms-cache/src/data.rs`, `serialize.rs`, `freshness.rs`). Do not implement until the DD.UA decoder and nonzero galaxy policy are supported.
3. **Exact regression oracle already available:** supplied `0x212B0004B2446A` must produce `212B04B2446A` with portal field groups `P=2`, `SSS=12B`, `YY=04`, `ZZZ=B24`, `XXX=46A` and independently supported expected fields; retain the portal-shaped `0x212B04B2446A` control as a negative control, not an accepted save-format case. Add paired production-derived system and planet values where their packed identity differs, and assert a find result uses the matched planet's glyph index.
4. **Separate base assignment:** require at least one sanitized persistent base address paired with an independent expanded/teleport location and a nonzero galaxy if possible. Only then decide whether its decoder is shared with discovery, and update the watch/show/base route or cache path under its own explicit assignment.
5. **Owner decisions before implementation:** raw `--ga` meaning and compatibility policy; signed negative integer policy; zero/sentinel and missing-expanded-field policy; out-of-width reject/truncate policy; source of galaxy for each packed field; query glyph behavior when system and planet indexes differ; and cache format invalidation/versioning. Do not turn absence or parse failure into a successful default address.

Source-confirmed defects include the reproduced low-48 DD.UA output and forced galaxy zero in current discovery/base conversions; unresolved hypotheses include the full packed formats, base/discovery equivalence, and generalized galaxy layout. This slice makes no production or fixture changes.
